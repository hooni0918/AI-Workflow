# Testing Strategy — 테스트 품질 기준

"테스트를 작성했고 통과했다"를 넘어, **요구사항의 실패·경계 상황을 검토했고 테스트가 실제 코드 오류를 잡는지 실행으로 확인했다**를 완료 기준으로 삼기 위한 기준의 단일 출처다. 플랫폼·도구와 무관한 기준만 둔다. 실행 명령과 도구 설정은 프로젝트 프로필이 공급한다.

## 테스트 의도

구현 전에 테스트 의도를 적는다. 표식 위치는 [assumptions.md](assumptions.md) 「단위 테스트 프레임워크」의 테스트 TODO다. 의도마다 다음을 담는다.

- **입력 조건**: 어떤 상태·입력에서
- **기대 결과**: 무엇이 관찰돼야 하는가. 반환값뿐 아니라 남아야 하는 상태까지 적는다 (예: 거절 후 잔액 유지)
- **요구사항 근거**: 기대가 어디서 왔는가 — 원본 자료의 위치나 문장. 근거가 "현재 구현이 그렇게 동작한다"면 의도가 아니다

### 상황 고르기

정상·실패·경계 상황을 기능에 맞춰 고른다. 개수를 채우려고 의미 없는 케이스를 만들지 않는다.

- **경계**: 조건 결과가 바뀌는 지점 — 같은 값, 바로 위, 바로 아래. 빈 값과 최대·최소
- **실패**: 요구사항이 거절·오류로 정한 입력, 그리고 그때 바뀌지 않아야 하는 상태

예: "잔액이 결제금액 이상이면 결제 가능"

- 잔액 충분 → 성공하며 정확한 금액 차감
- 잔액 부족 → 거절하며 잔액 유지
- 잔액과 금액 동일 → 성공하며 잔액 0

### 요구사항에 답이 없을 때

기대 동작을 지어내지 않는다. 의도를 질문으로 표식하고 사용자 결정을 받는다. 현재 구현의 동작을 기대값으로 옮겨 적는 것도 지어내기다.

예: 위 결제 규칙에서 "0원 결제"는 요구사항에 없다 — 성공·거절 중 하나를 고르지 않고 질문으로 올린다.

### 의도 목록 리뷰

리뷰어는 테스트 의도 목록을 **사용자가 제공한 원본 요구사항**과 대조해 빠진 실패·경계 상황을 찾는다. AI가 정리한 요구사항 요약은 대조 기준이 아니다.

## 변이 검사

구현 코드의 조건·연산자를 일부러 조금 바꾼 **변이**를 만들고, 기존 테스트가 실패하는지 실행해 본다. 테스트가 실패하면 그 변이를 잡은 것이다. 테스트가 통과하는 것과 오류를 잡는 것이 별개임을 확인하는 수단이다. 빠진 요구사항까지 찾아 주지는 않으므로 「테스트 의도」와 함께 쓴다.

### 검사 범위

- **로직이 바뀐 줄**: 기준 브랜치 대비 바뀐 로직 줄의 변이만 판정한다. 도구가 파일 단위로 돌아도 범위 밖 변이는 판정에 넣지 않는다
- **테스트만 바뀐 모듈**: 어느 로직을 겨냥했는지 알 수 없으므로 그 모듈의 로직 전체로 넓힌다
- **검사 설정에 없는 위치의 로직 파일이 바뀜**: 범위를 정하지 못한 것이다. 조용히 빼지 않고 검사 미완료로 둔다. 검사 대상이 아닌 위치(예: 화면 코드)는 설정에 명시해 뺀다
- **로직 파일이 바뀌지 않음**(문서·리소스만 바뀜): 해당 없음. 바뀐 파일 목록을 근거로 남긴다

### 상태별 판정

결과 상태는 도구들이 공통으로 내보내는 Stryker 보고서 형식(mutation-testing-report-schema)의 값을 쓴다. 도구마다 시간 초과·런타임 오류를 "잡음"으로 세는지가 다르다(Stryker는 시간 초과를 잡음으로, PIT는 런타임 오류를 잡음으로 센다). 상태만으로는 변이가 만든 멈춤·충돌인지 실행 환경 문제인지 구분되지 않으므로, 여기서는 자동으로 잡음 처리하지 않는다.

| 상태 | 뜻 | 판정 |
|---|---|---|
| Killed | 테스트가 실패해 변이를 잡음 | 검출 |
| Survived | 변이 후에도 테스트가 통과 | 미해결 — 요구사항과 대조해 테스트 누락인지 약한 단언인지 판단하고 보강 |
| NoCoverage | 변이 지점을 실행하는 테스트가 없음 | 미해결 — 테스트 보강 |
| Timeout | 제한 시간 안에 테스트가 끝나지 않음 | 미해결 — 제한을 늘려 다시 돌리거나, 변이가 무한 반복을 만든 근거를 판단 기록으로 남김 |
| RuntimeError | 테스트가 실패 판정 없이 비정상 종료 | 미해결 — 다시 돌려도 같으면 판단 기록으로 남김 |
| CompileError | 변이 코드가 컴파일되지 않음 | 제외 — 테스트가 잡은 것으로 세지 않는다 |
| Ignored | 도구가 실행하지 않음(제외 주석·설정) | 미해결 — 승인된 판단 기록이 있을 때만 해소 |
| Pending | 실행되지 않음 | 검사 미완료 |

### 검사 미완료

다음은 통과도 실패도 아닌 **검사 미완료**다. 성공으로 처리하지 않는다.

- 변이를 넣기 전 기준 테스트가 실패
- 도구 오류, 결과 파일 없음, 결과 형식 불일치
- 범위 안 로직 파일이 결과에 아예 나타나지 않음 — 도구가 그 파일을 분석했다는 증거가 없다. 분석했는데 변이 지점이 없는 것(해당 없음)과 구분한다
- 범위 안 변이가 전부 CompileError — 실제로는 아무것도 검사하지 못했다
- 결과가 현재 코드·테스트·설정과 맞지 않음 — 검사 뒤 내용이 바뀌었다

### 완료 기준

검사 범위 안 **미해결 0건, 미완료 사유 0건**. 점수 100%가 목표가 아니다 — 점수 정의(분모에서 무엇을 빼는지)가 도구마다 다르다.

### 판단 기록

미해결 변이 가운데 테스트로 잡을 수 없거나 잡을 필요가 없는 것은 판단 기록으로 해소한다.

- **결과가 같은 변이**: 바꿔도 관찰 가능한 동작이 같아 어떤 테스트로도 잡을 수 없는 변이 (예: 이미 앞에서 걸러진 값에 대한 조건)
- 기록에는 변이 식별(파일, 원래 줄 내용, 변이 종류, 바뀐 값), 판단 종류, 근거, 승인자를 담는다
- **사람이 승인한 기록만** 해소로 친다. AI는 근거를 붙여 제안까지만 한다
- 원래 줄 내용이 바뀌면 기록은 더 이상 그 변이에 맞지 않는다 — 코드가 바뀌었으니 다시 판단한다

### 금지

- 미해결을 없애려고 기대값을 현재 구현에 맞추거나 단언을 약하게 바꾸기
- 검사 범위 줄이기 — 도구의 제외 설정·제외 주석 추가, 변이 종류 끄기, 모듈 범위 축소. 꼭 필요하면 판단 기록과 같은 승인을 거친다
- 결과가 같은 변이 판정을 근거 없이 내리거나 스스로 승인하기
