# Test Quality

AI가 쓴 테스트가 실제로 오류를 잡는지 실행해서 확인하는 스킬입니다. 구현 코드를 일부러 조금 바꿔 보고(변이), 테스트가 그 변화를 알아채는지 봅니다.

## 동기

테스트가 통과한다는 것과 테스트가 오류를 잡는다는 것은 다른 이야기입니다. AI는 정상 상황만 테스트하거나, 지금 구현이 내놓는 값을 그대로 기대값으로 적고 "통과"로 끝내기 쉽습니다. 그러면 테스트는 초록불인데 정작 버그는 그대로 지나갑니다.

그래서 완료 기준을 넓혔습니다. "테스트를 쓰고 통과했다"가 아니라 "요구사항의 실패·경계 상황을 검토했고, 테스트가 코드 오류를 잡는지도 실행으로 확인했다"가 완료입니다.

## 어떻게 확인하나

`>=`를 `>`로, `&&`를 `||`로, `return false`를 `return true`로 바꾸는 식의 작은 변화를 코드에 넣고 테스트를 다시 돌립니다. 테스트가 실패하면 그 변화를 잡은 것이고, 그래도 통과하면 테스트에 구멍이 있다는 신호입니다.

예를 들어 "잔액이 결제금액 이상이면 결제" 규칙에 정상 결제 테스트만 있으면, `>=`를 `>`로 바꿔도 테스트가 통과합니다. 잔액과 금액이 같은 경우를 아무도 확인하지 않기 때문입니다. 그 테스트를 추가하면 같은 변화가 잡힙니다.

다만 이 방법은 이미 있는 코드가 잘 테스트됐는지만 봅니다. 요구사항 자체가 빠진 것은 찾지 못하므로, 구현 전에 요구사항에서 실패·경계 상황을 뽑아 테스트 의도로 적는 단계와 함께 씁니다.

## 판정

바뀐 코드에서 나온 변화만 봅니다. 결과는 세 가지입니다.

- **통과**: 잡지 못한 변화가 하나도 남지 않음
- **미해결**: 잡지 못한 변화가 남음. 테스트를 보강하거나, 요구사항에 답이 없으면 사람에게 묻거나, 바꿔도 동작이 같은 변화라면 근거를 적어 사람의 승인을 받습니다
- **검사 미완료**: 도구가 실패했거나, 결과가 없거나, 검사한 뒤 코드가 바뀌었음. 통과로 치지 않습니다

점수 100%를 목표로 하지 않습니다. 남은 것이 전부 처리됐는지가 기준입니다. 판정 기준 전체는 [test-quality.md](../../contexts/testing-strategy/test-quality.md)에 있습니다.

## 도구

변화를 만들고 테스트를 돌리는 일은 언어별 도구가 하고, 이 스킬의 실행기는 그 결과를 같은 기준으로 판정합니다. 도구가 바뀌어도 판정은 그대로입니다.

Swift는 [swift-mutation-testing](https://github.com/ericodx/swift-mutation-testing) 1.5.1로 시작합니다. 후보였던 Muter는 경계 변화(`>=`→`>`)를 만들지 못하고, 최신 코드가 변화를 실제로 넣지 않은 채 결과만 내는 버그가 있었으며, 실제 iOS 모듈에서 변화 7개에 64분이 걸리고 6개가 시간 초과였습니다. Flutter용 도구는 아직 정하지 않았습니다.

## 쓰임새

### 워크플로우 구현 단계

ios-workflow의 구현 단계가 끝날 때 바뀐 로직에 검사를 돌리고, 최종 점검에서 결과가 마지막 코드와 맞는지 다시 확인합니다.

### 앱 CI

같은 실행기를 앱의 CI에서 부릅니다. 스킬 문구만으로는 검사를 건너뛰는 것을 막을 수 없기 때문입니다. CI에서 돌리는 것과 머지를 실제로 막는 것은 별개라서, 앱 저장소에서 이 검사를 필수 상태 검사로 지정해야 머지가 막힙니다.
