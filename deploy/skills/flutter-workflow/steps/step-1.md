# Step 1: 배경 파악 · 입력 판별 · 분할 판단

> **이 단계의 목표: 작업의 문제/목표를 정의하고(도메인·제품 관점, 코드 분석 아님), 입력 종류를 판별하고, PR 분할을 결정한다.**

step-1은 PLAN 세션의 앞부분이다. 여기서 배경을 확정하면 **같은 PLAN 세션 안에서** 곧바로 [step-2](step-2.md)(과제 정의·구현 방침·브랜치/워크트리)로 이어진다. step-1 자체는 후속 세션을 spawn하지 않는다 — IMPL 세션 안내는 step-2 종료에서 발동한다.

절차: **1.0 입력 판별 → 1.1 자료 받기 → 1.2 requirement-review(신규일 때) → 분할 판단**.

**전체 작업당 1회다.** step-1의 배경 파악·입력 판별·분할 판단은 첫 PLAN에서만 수행한다. 멀티 PR의 2번째 이후 PLAN(`PLAN 2` 등)은 step-1을 건너뛰고 `background/consumable/project.md`를 읽어 step-2부터 진행한다. 단일 PR이면 step-1은 항상 실행한다.

## Step 1.0 입력 판별

자료를 받기 전에 이 작업의 입력 종류를 먼저 판별한다. 종류에 따라 이후 절차가 갈린다.

- **이관**: 기존 iOS 네이티브 화면/기능을 flutter로 옮긴다. → 아래 「이관: 로직 계약 추출」.
- **신규**: 기획서·디자인 시안으로 새 화면/기능을 만든다. → Step 1.2 requirement-review(screen-type 4종) 수행.
- **버그**: 버그 리포트를 수정 PR로 만든다. → 재현 경로·기대/실제 동작을 받아 근본 원인을 파악한다(“왜?”를 근본 원인까지 반복). 최소 수정 범위를 확정하고, 영향 받는 화면에만 Step 1.2의 공통 엣지케이스 체크리스트를 적용한다.

figma/시안 유무는 여기서 자동 판별한다(입력에 figma URL·캡처가 있으면 있음, 없으면 없음). 별도 모드 인자는 받지 않는다.

### 이관: 로직 계약 추출

이관 입력이면 자료 수집과 함께 **iOS 원본 소스 경로**를 수집하고, 원본에서 로직 계약을 추출해 `retained/logic-contract.md`에 정리한다.

추출 대상: **state / 이벤트 / API 호출 / 엣지케이스 / 문구(카피)** 를 iOS 원본 코드에서 그대로 뽑아 적는다.

- 이 파일은 이후 IMPL 검증을 빠르게 하기 위한 **캐시**다. **진실 원천은 iOS 원본 코드 재독**이며, logic-contract.md를 진실로 삼아 자기증명하지 않는다 (IMPL에서 원본을 다시 읽어 대조).
- 화면 스펙이 원본에 이미 정의돼 있으므로 이관은 requirement-review(Step 1.2)를 건너뛴다. 다만 플랫폼 차이로 새로 결정해야 하는 엣지케이스(다크모드·텍스트 스케일 등)는 Step 1.2의 공통 체크리스트로 점검한다.

## Step 1.1 자료 받기

### 자료 수집 점검

외부에서 시안·기획서·figma 자료를 받는 케이스라면, 자료 수집 방식이 적절한지 점검한다. 자료를 아직 받기 전이면 능동 안내, 이미 받았는데 흐릿하면 영역을 짚어 다시 요청한다.

**step-1.1은 자료의 단일 수집 지점이다.** 기획·요구사항과 함께 **사용 가능한 figma/시안 자료를 여기서 전부** 받아 저장한다 (figma URL·캡처 → `retained/figma-url.md`·`retained/figma/`). 다운스트림(requirement-review·step-2·IMPL)은 이 수집분을 *참조*하며 자료를 재요청하지 않는다.

figma/시안이 없으면(예: 내부 도구, 아직 시안이 없는 신규 화면) 자료 “받기” 대신 사용자와 함께 스펙을 **정의**한다. 정의는 Step 1.2 requirement-review에서 `screen.md`로 수행한다. 이 단계에서는 사용자가 이미 가진 참고 자료(디자인시스템 소스, 기존 코드 등)만 수집한다.

### 컨벤션 소스 수집 — 이름 스캔 선제안 + conventions-index.md

프로젝트 컨벤션 소스 수집의 **단일 지점**이다. 이후 단계는 여기서 만든 인덱스를 소비만 하고 재수집·재질문하지 않는다.

1. **이름 스캔 선제안**: 작업 레포가 존재하면 Glob으로 컨벤션 성격의 파일을 **이름만** 스캔한다 — `**/pubspec.yaml`, `analysis_options.yaml`, `**/CLAUDE.md`, `**/AGENTS.md`, `docs/**`, `l10n/strings.yaml`, 그 외 `*ARCHITECTURE*`·`*convention*` 류. 후보 목록을 사용자에게 선제안한 뒤 채택받는다. **이 단계에서 파일 내용은 읽지 않는다** (컨텍스트 오염 방지).
2. **사용자 보충**: "추가로 참고할 자료가 있나요? (예: 사내 컨벤션 가이드, 디자인시스템, 기존 기술 스택 제약 등)" 사용자 제공 원문은 `background/retained/`에 저장하고 인덱스에 등재한다.
3. **인덱스 작성**: 채택된 소스를 `background/retained/conventions-index.md`에 기록한다. 양식은 항목당 **"경로 + 한 줄 트리거(어떤 작업·모듈에서 봐야 하는지)"**. 본문 요약은 적지 않는다.
   - **빌드/검증 명령 단일 출처 등재**: [conventions/commands.md](../conventions/commands.md)를 인덱스에 등재한다. 트리거: "빌드·테스트·analyze·codegen·l10n·레이어 검증 명령이 필요할 때". [가정] 도구 환경(테스트 러너·CI)이 실제와 다르면 그 차이를 인덱스에 한 줄로 남긴다.
4. **레포가 아직 없으면** 스캔·인덱스 생성을 레포 확보 시점으로 미룬다.

**컨벤션 인덱스를 산출하기 전에 다운스트림(requirement-review·step-2)으로 진입하지 않는다.** 건너뛰고 진행하면 컨벤션 1차 소스를 거기서 재수집하게 되고, 같은 추출 패턴의 Reviewer가 그 누락을 못 잡는 자기증명 루프가 생긴다.

## Step 1.2 requirement-review 본체

**주로 신규 입력에서 수행한다.** 이관은 logic-contract.md 추출로 대체하고(플랫폼 차이 엣지케이스만 아래 체크리스트로 점검), 버그는 영향 받는 화면에만 아래 체크리스트를 적용한다.

### 화면 종류별 엣지케이스 선제 질문

모바일 화면은 기획서가 잘 다루지 않는 빈틈이 많다. 각 화면을 아래 **모바일 공통 엣지케이스**에 대고 검토하고, 정의되지 않은 항목을 사용자에게 선제 질문한다. 화면 종류별 추가 체크리스트는 해당 화면에 함께 적용한다.

**모바일 공통 엣지케이스 (모든 화면)**:
- **다크모드**: 라이트/다크 양쪽에서 색·이미지·그림자가 정의되어 있는가? `ThemeMode`/테마 확장에 다크 변형이 있는가?
- **텍스트 스케일**: 시스템 글자 크기를 최대(접근성 크기 포함)로 키웠을 때 레이아웃이 깨지지 않는가? `MediaQuery.textScaler` 최대에서 줄바꿈/말줄임/스크롤 처리가 정의되어 있는가?
- **SafeArea**: 무시할 영역(배경)과 지킬 영역(콘텐츠·버튼)이 구분되어 있는가? `SafeArea`/`MediaQuery.padding` 적용 지점이 정해져 있는가?
- **빈 상태**: 데이터가 0건일 때 화면이 정의되어 있는가? (아래 리스트 화면 체크리스트와 연동)
- **딥링크**: 외부에서 이 화면으로 직접 진입할 수 있는가? 선행 데이터 없이 진입하면 어떻게 되는가?
- **백그라운드 복귀**: 백그라운드에 갔다가 복귀하면 데이터 갱신·타이머·인증 만료 처리가 정의되어 있는가?
- **회전**: 가로/세로 회전 지원 여부와, 회전 시 레이아웃 변화가 정해져 있는가?
- **접근성**: 인터랙션 요소의 `Semantics` 레이블과 테스트 셀렉터 `Key`(`find.byKey`) 네이밍이 정의되어 있는가? (Key는 위젯 테스트의 셀렉터를 겸한다)

화면 종류별 추가 체크리스트:
- 리스트형: [requirement-review/screen-type/list.md](../requirement-review/screen-type/list.md)
- 상세형: [requirement-review/screen-type/detail.md](../requirement-review/screen-type/detail.md)
- 폼형: [requirement-review/screen-type/form.md](../requirement-review/screen-type/form.md)
- 순차 플로우: [requirement-review/screen-type/sequential-flow.md](../requirement-review/screen-type/sequential-flow.md)

**진행 방식**: AI는 요구사항을 비판적으로 분석하고, 발견한 빈틈을 질문으로 제시한다. 단정하지 않고 장단점을 함께 설명한다. 화면마다 같이 분석 → [`/discussion`](../../discussion/SKILL.md)으로 미결 항목 결론 → 산출물 확정. 확정 내용은 `pr{N}/consumable/screen.md`(화면별)·`background/`(공통)에 기록하고, 사용자가 판단할 수 없는 항목은 TODO로 분류한다.

### 중복 조기 발견

requirement-review 단계에서 디자인·컴포넌트 중복이 있으면 **사용자에게 명시 통보**한다. 분석 산출물에 묻어서 흡수만 시키지 않는다. 형식: "시안 카드 N종에서 공통 골격 발견 → 공통 위젯 추출 대상. 지금 통합 결정 vs 나중에 PLAN으로 미루기 중 선택".

### 작업 익숙도 판별

사용자에게 "이번 작업에서 처음 다루는 기술이나 낯선 영역이 있나요?"를 확인한다. 낯선 작업이라면:

1. 공부 세션을 위한 인수인계 문서를 작성한다 (왜 필요한지 / 알아야 하는 키워드·핵심 API를 학습 순서대로). 구체적 학습 방법(how)은 공부 세션에서 결정.
2. **별도 세션에서 인수인계 문서 기반으로 병행 학습**하면서, 이 세션에서는 기획을 계속 진행하도록 안내.
3. 사용자는 방향 잡기(라이브러리 선택, 참조할 원본 코드 지정)에 집중, 구현 판단은 AI가 맡되 리뷰를 더 꼼꼼히 받는 구조.

인수인계 문서가 작성되었으면 이후 PLAN 세션 진입 안내 시 "학습 완료 뒤 진입하라" 조건을 함께 안내한다 (SKILL.md 「학습 인수인계 후 세션 진입 대기」).

## 분할 판단 — 단일 PR vs 멀티 PR

배경이 확정되면 작업을 몇 개의 PR로 나눌지 판단한다.

### 작업 크기 판단

- **작은 작업** (커밋 3개 이하): 단일 PR이 디폴트. 분할 절차를 건너뛰고 사용자에게 스킵을 제안한다.
- **큰 작업** (커밋 4개 이상, 또는 여러 도메인 포함): PR 분할 전략을 수립한다.

### PR 분할 원칙

- **한 번에 하나의 PR, 하나의 구체적인 기능**만 다룬다.
- **의존성 순서**: 공통/하위 레이어 → 개별 화면. clean architecture 레이어 방향(단방향)을 따른다 — `feature → domain ← data`, domain은 최내곽(feature·data 의존 금지), core·design_system은 횡단. 레이어 역방향 의존이 생기지 않도록 분할한다.
  - 레이어 방향 검증은 [conventions/commands.md](../conventions/commands.md)의 레이어 검증 절차(각 `pubspec.yaml`의 `path:` 의존을 grep해 방향과 대조)를 따른다. 정확한 허용 방향은 이 스킬이 단정하지 않고 코드베이스 실측과 [conventions/review-checklist.md](../conventions/review-checklist.md)의 리뷰 채굴 근거로 확인한다 (레이어는 리뷰 최다 지적 축).
- **기술적 과제는 step-2에서** — 이 단계는 PR 분할에만 집중한다.
- **멀티 PR은 순차로 진행한다.** 이전 PR을 머지한 뒤 다음 `PLAN`(N+1)을 진입한다. 여러 PLAN을 동시에 열어 병렬화하지 않는다.

### 기획 점검 (TODO 식별)

PR 분할 초안 작성 후, 각 PR별로 사용자에게 사전 확인이 필요한 TODO가 있는지 확인한다.

### Step 1 폴더 재정비

Step 1에서 생성된 `pr{N}/` 폴더는 화면 플로우 순서 기준이다. PR 경계가 확정되면 번호가 달라질 수 있다.

- 경계 확정 후 `pr{N}` 폴더를 실제 PR 번호에 맞게 rename/merge한다.
- `project.md`의 "참고 background 파일" 경로도 함께 갱신한다.

### 산출물: `background/consumable/project.md`

멀티 PR이면 PR별로 아래 항목을 포함해 작성한다:
- PR 제목
- 범위
- 참고 background 파일
- 기획 확인 필요 사항 (TODO)

### 보고 내용

- 총 PR 수와 각 PR 범위 한 줄 요약
- PR 간 의존 순서
- 사용자 판단이 필요한 열린 질문 (있는 경우)

## Step 1 종료 — 배경 확정 보고

step-1 종료 = 입력 종류 확정 + (이관이면) `retained/logic-contract.md` · (신규면) `screen.md` 산출 + 컨벤션 인덱스 산출 + (멀티 PR이면) `background/consumable/project.md` 산출.

배경이 확정됐음을 보고하고, **같은 PLAN 세션 안에서** [step-2](step-2.md)(과제 정의·구현 방침·브랜치/워크트리 생성)로 이어간다. step-1은 후속 세션 spawn 분기점이 아니므로 여기서 세션 안내를 발동하지 않는다 — IMPL 세션 안내는 step-2 종료에서 발동한다.
